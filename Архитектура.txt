## 1. Короткий вывод

AgentOS — Markdown-first система управления AI-assisted software development внутри репозитория.

AgentOS не является автономным агентом. AgentOS является governance/runtime-слоем, который задаёт правила работы агента с задачами, состоянием, scope, validation, evidence и human approval.

Главная цель архитектуры — не ускорить агента любой ценой, а не дать ему создать ложный PASS, скрытый approval, неконтролируемый lifecycle mutation или перенос legacy-ошибок в новый проект.

```text
Strict inside.
Simple outside.
Human decides.
```

## 3. Назначение архитектуры

Архитектура должна решить 7 задач:

1. Дать пользователю простой вход: “Начнём проект”.
2. Превратить идею в ТЗ, задачи и work package.
3. Дать агенту только один следующий разрешённый шаг.
4. Проверять scope, state, context, validation и evidence.
5. Не допустить ложного PASS.
6. Не допустить симуляции human approval.
7. Поддержать clean template distribution.

Архитектура не является:

- autonomous agent platform;
- full RAG/vector DB platform;
- SaaS dashboard;
- medical system;
- release approval system;
- replacement for human review;
- self-healing business logic engine.

## 5. Базовые инварианты AgentOS

Эти правила нельзя переопределить через pipeline, registry, context, SQLite, RAG, CI, generated files, reports, audit, agent output, prompt pack или SaaS UI.

```text
PASS ≠ approval.
Evidence ≠ approval.
CI PASS ≠ approval.
WARN ≠ clean PASS.
Signed commit ≠ approval.
Decision Record ≠ approval.
Context Pack ≠ approval.
Work Package ≠ approval.
Task test PASS ≠ approval.
Self-test PASS ≠ approval.
Safety regression PASS ≠ approval.
Human approval нельзя симулировать.
```

Fail-closed:

```text
UNKNOWN → BLOCKED.
NOT_RUN → BLOCKED.
NO_CONTEXT_FOUND → BLOCKED.
UNKNOWN_REPO_STATE → BLOCKED.
UNKNOWN_CROSS_REPO_IMPACT → BLOCKED.
BOOTSTRAP_UNKNOWN → BLOCKED.
BOOTSTRAP_NOT_RUN → BLOCKED.
SOURCE_DOCUMENT_CONFLICT → BLOCKED.
DUPLICATE_AUTHORITY → BLOCKED.
```

Source-of-truth:

```text
Markdown/YAML = source of truth.
JSON/index/cache = derived only.
SQLite = cache only.
RAG result = retrieved data, not authority.
Generated artifact = derived reflection, not authority.
Reports = evidence only.
Audit = evidence only.
Dashboard = read model, not authority.
```

Lifecycle:

- scope задачи не расширяется без явного разрешения;
- protected/canonical files требуют human checkpoint;
- multi-repo changes требуют human checkpoint;
- cascade execution запрещён без отдельного human checkpoint;
- один сигнал — одно действие;
- следующий milestone/stage не запускается автоматически.

Priority:

```text
Safety > speed.
Truthful status > convenience.
Human approval > automation.
Traceability > convenience.
Verifiability > efficiency.
Architecture correctness > short-term velocity.
```

## 8. Core Ownership Model

### 8.1 User-owned root

Корень проекта принадлежит пользователю. Агент не может:

- считать весь root своей зоной;
- удалять пользовательские файлы;
- перемещать пользовательский проект;
- превращать root в AgentOS-owned namespace;
- создавать скрытую lifecycle authority в root.

### 8.2 AgentOS-owned core

`agentos/` принадлежит AgentOS и содержит governed core, contracts, registry, state, pipelines, validation, templates, reports and approval surfaces.

Агент не может:

- удалять `agentos/`;
- самовольно заменять `agentos/`;
- переписывать protected/canonical файлы без checkpoint;
- repair meaning/state/approval;
- считать generated/cache источником истины.

### 8.3 Local runtime/cache

`.agentos/` является локальной runtime/cache зоной.

Правила:

```text
.agentos/ must be gitignored.
.agentos/ must not enter GitHub template repo.
.agentos/ may be rebuilt when safe.
.agentos/ is never source of truth.
Loss of .agentos/ does not mean loss of task state or approval.
```

Пользователь не должен вручную управлять внутренними механизмами: registry, pipeline yaml, context sqlite, generated indexes, checksums, chunking, resolver internals, cross-repo contracts.

Пользователь видит guided workflow:

## 11. Architecture Layers

| Layer | Назначение |
|---|---|
| Bootstrap | безопасный старт через `llms.txt` и preflight |
| Governance | инварианты, authority, write policy, approval boundaries |
| Contract | формальные runtime/validation/recovery/update/module semantics |
| Registry | карта documents/features/modules/scripts/schemas/templates/repos |
| State | task/run/approval/snapshot lifecycle facts |
| Resolver | один следующий безопасный шаг |
| Pipeline | bounded flows без cascade automation |
| Validation | deterministic checks, false PASS resistance, negative cases |
| Context | retrieval-only context selection |
| Evidence | reports, work packages, decision records, context packs |
| Audit | append-only evidence of events |

| Install/Update | install, update, removal, clean template export |
| Module | optional modules без расширения core permissions |

## 12. Bootstrap Layer

`llms.txt` — bootstrap pointer.

Он должен:

- указать, где установлен AgentOS;
- указать первые обязательные файлы для чтения;
- закрепить базовые safety rules;
- направить агента к `agentos/agentos.py`;
- не быть runtime authority;
- не быть source of truth для lifecycle, validation или approval.

Запрещено:

```text
llms.txt as PRIMARY authority
llms.txt as SOURCE_OF_TRUTH
llms.txt as full rule dump
llms.txt as lifecycle authority
llms.txt as approval authority
```

## 13. Governance Layer

Минимальные governance rules:

- protected paths require checkpoint;
- approval cannot be simulated;
- reports are evidence only;
- validation cannot mutate lifecycle;
- generated/cache cannot override canonical text;
- unknown blocks;
- not_run blocks;
- one signal triggers one action;
- cascade execution requires human checkpoint;
- task scope cannot expand silently.

Governance layer сильнее tutor hints, prompt packs, generated indexes, dashboard, agent report, CI green result, work package and context pack.

## 14. Contract / Registry / State / Resolver / Pipeline

Contracts define allowed meaning. Implementation must obey contract. Generated artifacts cannot override contract.

Registry maps declared surfaces but cannot approve, execute, complete task or replace human checkpoint.

State records lifecycle facts. Agent report, decision record and validation PASS are not lifecycle state.

Resolver returns one allowed next action and cannot execute commands, mutate files, create approval, complete task or start next stage.

Pipeline defines bounded flows but cannot approve, skip resolver, mutate lifecycle without state rules or run cascade execution.

## 15. Documentation Factory and Work Package Boundary

Controlled chain:

```text
problem interview
  ↓
product brief
  ↓
spec draft
  ↓
spec validation
  ↓
human spec review
  ↓
task drafts
  ↓
task scope validation
  ↓
human task review
  ↓
work package
  ↓
controlled execution request
```

Boundary:

```text
Interview draft is not approved spec.
Spec draft is not execution permission.
Task draft is not active task.
Work package is not approval.
Validation PASS is not approval.
Human decision remains required.
```

Work package is bounded input for agent execution. It is not source of truth, approval authority or lifecycle authority.

## 16. Validation / Evidence / Approval

Validation checks deterministic things:

- file structure;
- required fields;
- allowed statuses;
- forbidden claims;
- exit-code/result consistency;
- negative cases;
- protected/canonical boundaries;
- scope compliance.

Validation cannot approve, mutate lifecycle or mark task done by itself.

Evidence records observable facts: reports, stdout/stderr, exit codes, snapshots, hashes, validation outputs. Evidence is material for human review, not approval.

Human approval is separate and higher than PASS/evidence/CI. Agent cannot create or simulate it.

## 17. Report Safety / Audit

Reports must not claim:

```text
approved
human approved
done without review
merged
released
execution authorized
lifecycle mutated
```

unless a trusted human checkpoint or actual recorded state proves it.

Audit is evidence only. Audit cannot approve, repair, mutate lifecycle or overwrite history.

## 18. Context / Generated / Cache Boundary

Context layer selects relevant context and must minimize prompt bloat.

RAG-light and SQLite are allowed only as retrieval/cache/navigation helpers:

```text
Markdown/YAML = meaning.
JSON/index = navigation.
SQLite = speed.
RAG result = retrieved data.
Context Pack = task-applicable context.
Verification = compliance with selected context.
```

Generated artifacts cannot become source of truth.

## 19. Degradation / Concurrency / Recovery

If critical input is missing, stale, conflicting or unknown, AgentOS must degrade to blocked or review-required state.

Concurrency model must prevent competing mutations, stale approvals and conflicting task states.

Recovery may restore structure or explain blockers. Recovery must not self-heal business logic, approval, protected/canonical meaning or lifecycle decisions.

## 20. Install / Update / Removal / Template Export

Install:

- dry-run first;
- no overwrite by default;
- no delete by default;
- no commit/push;
- no approval claim.

Update:

- diff required;
- protected paths require checkpoint;
- source-of-truth changes require explicit authorization;
- generated/cache rebuild allowed only when safe.

Removal:

- must preserve user files;
- must not delete approvals/evidence without human instruction;
- must explain what remains.

Clean template must not include old reports, approvals, audit logs, cache, secrets, private context or local runtime artifacts.

## 21. Feature and Module Lifecycle

Every new feature must have:

- owner layer;
- metric;
- source-of-truth impact review;
- context growth review;
- validation plan;
- negative cases;
- rollback or deprecation plan if relevant.

Future feature candidates live in:

```text
08_Future_Feature_Candidates_Parking_Lot.txt
```

They are not roadmap items and not implementation permission.

## 22. Core / SaaS / Domain Split

AgentOS core — governance engine for AI-assisted development.

SaaS — UX, onboarding, dashboard, collaboration and commercial layer.

Domain modules — optional external layers, for example medicine, design, product templates.

Медицина не входит в AgentOS core. Клинические решения требуют отдельного safety/compliance/privacy/liability слоя.

## 23. Cross-Repo / Security / Privacy Boundary

Cross-repo changes require explicit boundary, source mapping and human checkpoint. Unknown cross-repo impact blocks.

Security/privacy rules:

- no secrets in reports;
- no tokens in generated indexes;
- no private keys in templates;
- unknown data classification blocks export;
- medical/personal data requires separate access/storage/audit/deletion architecture.

## 24. Model Compatibility Boundary

AgentOS must work with different AI coding agents and IDEs through adapter/prompt-pack boundaries.

Adapters are derived/advisory. They cannot override core rules, approval boundaries, validation semantics or protected paths.

## 27. Stage 1 Gate Boundary

Stage 1 проверяет source pack и готовность к дальнейшему переносу смысла из legacy.

Stage 1 не выполняет:

- перенос проекта;
- перенос файлов;
- реализацию фич;
- deprecation execution;
- merge/release;
- lifecycle mutation;
- запуск Stage 2.

Stage 1 may only produce evidence and readiness reports.

## 28. Command Boundary

Команды AgentOS должны быть explicit, deterministic and scope-bound.

Запрещены команды, которые:

- скрыто меняют lifecycle;
- обходят resolver;
- создают approval;
- делают commit/push без разрешения;
- выполняют destructive operations без human authorization;
- стартуют следующий stage автоматически.

## 29. False PASS Resistance

False PASS resistance requires:

- result semantics;
- machine-readable outputs where needed;
- exit-code/result consistency;
- negative fixtures;
- evidence binding;
- forbidden-claim checks;
- separation of PASS, evidence, approval and lifecycle mutation.

## 30. Functional Parity Boundary

Functional parity means target behavior preserves or hardens important legacy behavior.

Parity PASS requires:

- legacy behavior identified;
- target behavior identified;
- owner layer defined;
- positive cases checked;
- negative cases verified;
- fail-closed preserved or hardened;
- approval boundary preserved;
- lifecycle boundary preserved;
- duplicate authority check passed;
- evidence refs present.

If parity is unknown, result blocks.
